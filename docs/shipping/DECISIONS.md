## ADR-OPS-001 · PostgreSQL-backed durable queue for V1

- **Status:** Accepted as the V1 provider/interface decision on 2026-09-14. This accepts the queue boundary and design, not worker execution or production qualification.
- **Context:** Web currently uses Vercel Node.js route handlers and Neon/PostgreSQL. Its schema already has tenant-scoped `jobs` and `outbox_events` tables with idempotency keys, attempts, due times, lease owner/expiry, and supporting indexes. The existing monitor route documents an external scheduler trigger. The actual Vercel plan and production environment matrix were not verifiable with the available Vercel token, so V1 must not depend on Vercel Cron frequency/precision.
- **Decision:** Use existing PostgreSQL as the durable source of truth for V1 job/outbox state. A scheduler is only a wake-up mechanism for a bounded worker; it does not own delivery state. Do not add Redis, managed queue SaaS, Vercel Workflow, in-process `Map`, `waitUntil`, or a new service solely for queueing. Existing Neon/Postgres is the only selected provider for this boundary. External side effects must be idempotent and driven from an outbox record committed with the authoritative state change.
- **Contract:** enqueue is idempotent by `(organizationId, kind, idempotencyKey)`; leasing claims only due work atomically and returns a fenced lease generation; expired/stale fences cannot acknowledge or mutate a newer lease; processing is at-least-once; retry time is explicit and bounded by configured worker policy; exhausted jobs enter a durable dead-letter state; only stable bounded error codes are persisted; tenant scheduling rotates through an opaque durable fairness cursor and limits per-tenant batch dominance; retries and outbox effects are observable and replay-safe.
- **Boundary:** `OPS-001` delivers this decision and provider-neutral interface only. Due-job production, concrete PostgreSQL claim SQL, fairness cursor schema/migration, worker runtime, retry policy values, DLQ operations, alerting, restore/replay drill, and production environment/scheduler verification remain separate backlog items. Do not claim the present schema implements the full contract until those items are tested.
- **Evidence:** Current `jobs`/`outbox_events` schema at Web source commit reviewed on 2026-09-14; existing monitor route references external cron-job.org as primary wake-up. Official Vercel docs state Hobby Cron is daily-only and timing is not guaranteed, while Cron invokes Functions subject to their limits: [Cron Jobs usage and pricing](https://vercel.com/docs/cron-jobs/usage-and-pricing). Therefore this decision does not assume a paid Vercel plan or strict trigger cadence.
- **Consequences:** No queue vendor key, new recurring spend, provider contract, or new service is required for V1. PostgreSQL throughput, atomic claim semantics under Neon HTTP, scheduler trigger ownership/frequency, cursor migration, idempotent effect handling, and backup/restore/replay still require qualification before activation.
- **Rollback:** Keep producers disabled until a compatible Postgres implementation and runtime acceptance exist. If Postgres capacity or deployed runtime constraints fail qualification, do not silently swap providers; amend this ADR with measured evidence and a separately reviewed migration/compatibility plan.
